# 插件「同进程隔离」进程级方案评估

> 状态：**第一步已实施**（档位 B，v0.5.2 / ADR-023）；档位 C 仍待条件 · 日期 2026-09-28 · 关联 ADR-016 / ADR-021 / ADR-023

## 1. 为什么评估这件事

当前插件与宿主**同进程、同权限、同 uid**（`packages/.../config/privilege`：`run-as=package`）。
这意味着插件代码可以：

| 能做什么 | 具体后果 |
|---|---|
| 读**整个进程内存** | 拿到 age 私钥（可解密**全部**备份）、主口令 `TRIM_PASSPHRASE`、所有 WebDAV 凭据明文 |
| 读写**任意文件** | 配置、密钥库 `keystore.age`、**主口令 `.passphrase`**、快照库 SQLite、宿主二进制 |
| 任意网络访问 | 外传上述任何数据 |
| 干扰宿主 | 改内存、阻塞线程（看门狗**无法强杀**单次阻塞 FFI） |

这不是「配置不当」——是**进程模型的固有属性**。ADR-016 已把它记为有意取舍
（`ctx` 非密码学凭证），`PLUGIN_ABI.md` §8 也如实写着「同进程、同权限」。
本文评估**把插件移出宿主进程**的代价与收益。

## 2. 实测事实（本机 fnOS，内核 6.18.18）

评估不能凭印象，以下全部本机实测：

| 事实 | 实测结果 | 对方案的影响 |
|---|---|---|
| 应用特权 | `CapEff=0000000000000000`，uid 982 | **无任何 capability** ⇒ 不能 `mount`/`chroot`/建 netns |
| 非特权 `unshare` | `unshare -U` → `EPERM`（此环境禁 userns） | 容器类方案（档位 E）无门 |
| `prctl(PR_SET_NO_NEW_PRIVS)` | 成功 | seccomp / Landlock 的**前置条件**可用 |
| **Landlock** | **ABI v7 可用**，`landlock_create_ruleset` 返回 7 | 无特权文件系统 + **TCP 端口**白名单 |
| Landlock 文件限制 | 允许 `/tmp` 后读 `/etc/hostname` 被挡 | ✅ 有效 |
| Landlock 网络限制 | 只允许 `:443` 后，连 `:22` → `EPERM` | ✅ **可按端口白名单**（ABI v4+） |
| **Landlock 作用域** | **per-thread**（多线程程序需每线程施加） | 见下，**这是关键约束** |
| Landlock 继承 | 施加后**新建**线程/`fork` 子进程**继承** | ✅ 可用于「专属线程池」 |
| Landlock 对**已存在**线程 | **不影响**（实测：施加前就运行的线程仍能读） | ⚠️ 无法收紧既有线程 |
| Landlock **不可逆** | 再施加「允许 `/`」的规则集后仍被挡 | ⚠️ 收紧即永久 |
| Landlock 挡 `/proc/<宿主pid>/mem` | **被挡**（`EPERM`） | ✅ **同 uid 跨进程读内存的通道被堵住** |
| Landlock 挡 `/proc/self` | **也被挡** | ⚠️ 必须**显式允许** `/proc/self`，否则插件运行环境异常 |
| `fork+exec` 成本 | **0.44 ms**（`/bin/true`，20 次均值） | 子进程方案**每次调用**的固定成本 |
| 插件产物类型 | `ELF 64-bit LSB shared object`（cdylib） | ⚠️ 不能直接 `exec`，需**新产物**：插件运行器 |

## 3. 一个必须先讲清的结论：进程隔离≠安全

**这是本次评估最重要的发现，也是最容易被误解的地方。**

把插件放进子进程，只解决「读宿主**内存**」。但子进程仍是**同一个 uid**，
而解密备份所需的材料分两处落在磁盘上：

| 文件 | 权限 | 内容 | 单独拿到有用吗 |
|---|---|---|---|
| `keystore.age` | `644` | age 私钥（`AGE-SECRET-KEY-1…`）**经口令加密** | ❌ 只是密文 |
| `.passphrase` | `600` | 加密口令（安装向导写入） | ⚠️ 配合上一行即可解密 |

```console
$ head -c 16 /vol1/@appconf/fn-kzwr-backup/keystore.age   # age-encryption.org/v1
$ ls -la /vol1/@appconf/fn-kzwr-backup/keystore.age /vol1/@appconf/fn-kzwr-backup/.passphrase
-rw-r--r-- 1 fnkzwrbackup fnkzwrbackup keystore.age   # 644：本机**任何用户**可读（但是密文）
-rw------- 1 fnkzwrbackup fnkzwrbackup .passphrase    # 600：仅应用用户可读
```

**关键判断**：应用进程与这两个文件的属主是**同一个 uid**（实测都是 `fnkzwrbackup`=982）。

- `600` 权限**挡不住同 uid** ⇒ 同 uid 的子进程可以读 `.passphrase`；
- `644` 的 `keystore.age` 本来就能读。

⇒ **同 uid 子进程可以同时拿到两者，进而解出 age 私钥**（该私钥能解密**全部**备份）。
效果与读宿主内存**等价** —— 但路径不是「直接读私钥文件」，而是
**「读密文 + 读口令 → 解密」两步**。

> ⚠️ 顺带更正一个常见误解：**`.passphrase` 才是真正的钥匙**。
> 它是**主口令** —— 不仅保护 age 私钥，还加密配置里的 WebDAV 凭据与插件数据。
> 只把 `keystore.age` 改成 600 **没有意义**，必须连 `.passphrase` 一起挡住。

因此：

> **纯进程隔离（不叠加文件系统限制）几乎不增加安全性** ——
> 子进程照样能读走「密文 + 口令」这两份材料。
> 真正的收益来自 **「地址空间分离 + Landlock 文件白名单」的组合**：
> 白名单必须**同时**排除 `keystore.age` **与** `.passphrase`（实务上按**目录整体**排除最稳）。
>
> **但实测发现一个例外（对本方案有利）**：Landlock 会一并挡住
> `/proc/<宿主pid>/mem` —— 那是同 uid 进程间读内存的**经典绕过通道**。
> 因此即使只用档位 B（同进程、仅线程隔离），也能堵住这条绕过路径，
> 只是**同一进程内**直接读指针仍然挡不住（那需要档位 C）。

这条结论改变了方案排序：**Landlock 不是可选项，是必要组成**；
且**保护对象清单**应是「配置目录 + 宿主数据目录」整体，而不是只盯 `keystore.age`。

## 4. 五个档位的对比

### 档位 A：Landlock 施加到现有 `spawn_blocking` 线程

```
宿主 → spawn_blocking(池线程) → 施加 Landlock → 调插件 → 返回
```

| 维度 | 评估 |
|---|---|
| 改动量 | 小（`cabi.rs`/`target_abi.rs` 的 FFI 包装处加 hook） |
| 隔离效果 | **差** |

**否决理由**：`spawn_blocking` 是 tokio 的**共享线程池**（线程复用）。
Landlock **不可逆** ⇒ 一旦在池线程上施加，该线程**永久**受限；
后续宿主自己的 `spawn_blocking` 任务（如配置读写、快照操作）若复用到这个线程，
会**莫名失败**。等于给宿主埋随机故障。

### 档位 B：每插件专属线程 + Landlock（**已实施** —— v0.5.2 / ADR-023）

```
宿主 → 该插件专属线程（首次使用时施加 Landlock）→ 调插件
                             ↑ 只有插件的调用跑在这里，永不归还池
```

| 维度 | 评估 |
|---|---|
| 改动量 | **中**：`cabi.rs`/`target_abi.rs` 改为投递到每插件专属线程；Landlock 封装 ~150 行 |
| 隔离效果 | **中**：挡住文件系统（密钥库/配置/快照）+ 网络（可选） |
| 挡住「读宿主内存」 | ❌ **不能**（同地址空间） |
| 性能 | 线程切换，**无** fork 成本 |
| 契约变更 | **零**（ABI 完全不变） |

**为什么推荐**：以最小代价拿到「插件碰不到密钥库文件」这一**最实际**的防护
（比「读内存」更容易被利用，且是持久化攻击）。

**已知局限**：
- 挡不住内存读 ⇒ 真正的恶意插件仍可窃取主口令（进而在**宿主**进程里解密）。
- `fork` 子进程继承限制 ⇒ 插件若自己 `fork`，子进程受限（这是好事）；
  但插件可以调 `unshare`？**不能**（无 capability）。
- Landlock 只管**文件路径**与 **TCP 端口**，不管 UDP、不管 `AF_UNIX`。
- `/proc/self` 会被一并挡住 ⇒ 白名单里**必须显式允许**（已实测：允许后
  `/proc/self/status`、`/proc/self/maps` 可读，而 `/proc/1/mem` 仍被挡）。

**已实测的白名单形状**（`expect` = 应允许 / `deny` = 应拒绝，全部符合预期）：

```
允许: /proc/self（读写）/ 插件数据目录（读写）/ /tmp（读写）/
      /etc/localtime + /usr（只读，动态库与时区）/ /dev/urandom
拒绝: keystore.age ✗ / **.passphrase ✗** / etc/shadow ✗ / proc/<宿主pid>/mem ✗ / 源码目录 ✗
      （keystore.age 是密文、.passphrase 是钥匙 ⇒ **两个都要挡**，缺一不可）
```

> **档位 B 的关键收益由此确立**：它不仅挡住「打开密钥库文件」，
> 还**顺带堵住了同 uid 进程间读内存的经典通道** `/proc/<pid>/mem`。
> 这比我最初的预期更好 —— 意味着档位 B 的防护面比「只挡文件」更宽。

### 档位 C：子进程 + 保留现有 C ABI

```
宿主 ──fork+exec──► 插件运行器（新二进制）──dlopen──► libfn_kzwr_plugin_kzwr.so
   │                                                      │
   └────────── fd / 共享内存传参 + 结果回传 ──────────────┘
```

| 维度 | 评估 |
|---|---|
| 改动量 | **大**：新增「插件运行器」二进制 + IPC 协议 + 每插件进程生命周期管理 |
| 隔离效果 | **高**：地址空间分离 + Landlock（挡住磁盘密钥） |
| 性能 | 每次调用 `fork+exec` 0.44ms（**每次动作用户感知不到**）；但传输路径要重做 |
| 契约变更 | **部分**：`ctx` 是裸指针跨进程无意义 ⇒ 改为整数 handle；`seal/unseal` 需转发 |

**最大难点是传输路径**，量化如下（默认块 1024 KiB）：

| 场景 | `write_chunk` 调用数 |
|---|---:|
| 1 GB 单文件 | 1,024 |
| 10 GB 单文件 | 10,240 |
| 50,000 个小文件 | ≈ 150,000（每文件 begin+chunk+end） |

当前传输是「宿主 `spawn_blocking` **逐块喂**插件」（`target_abi.rs:540`）。
跨进程后每块都要过 IPC ⇒ 必须改用 **fd 传递**（`SCM_RIGHTS` 把管道交给子进程，
密文流走内核管道，不过用户态 IPC）或**共享内存环形缓冲**。
这是可行的（也是 `plugins/*` 推块模型天然适配的），但工作量实打实。

**另一个权衡**：插件冷启动 = 建 tokio runtime + `reqwest::Client` 连接池
（`kzwr/src/rt.rs` 用 `OnceLock` 全局单例，**每进程一份**）。
⇒ 必须**每插件常驻一个进程**（不能每次调用都 fork），否则把 0.44ms 的
`exec` 成本换成几十 ms 的 runtime 重建。

### 档位 D：子进程 + 全新 IPC（放弃 C ABI）

彻底但**不建议**：等于把 ADR-013～021 六轮演进的契约全部推翻重做
（主表、能力表、目标表、SDK、`describe.json` 契约、签名机制）。
收益相对档位 C 只是「契约更干净」，成本却是数倍。

### 档位 E：容器 / namespace 隔离

`unshare` **本机实测 `EPERM`**（无 capability）。除非飞牛给应用 `CAP_SYS_ADMIN`
或放开发包（都不现实），此档**不可用**。

## 4.5 实施现状（v0.5.2 / ADR-023）

**已做**：

| 项 | 位置 | 说明 |
|---|---|---|
| 每插件专属线程 | `plugin/worker.rs` | 首次使用即施加沙箱；永不归还 tokio 共享池 |
| Landlock 绑定 | `plugin/sandbox.rs` | 结构体/常量按内核 UAPI 本地声明 |
| 降级策略 | 同上 | 内核不支持/施加失败 ⇒ 记警告继续，不阻断 |
| 逃生舱 | `FN_KZWR_NO_SANDBOX=1` | 误伤时立刻恢复可用，启用时记警告 |
| `keystore.age` 0600 | `infra/keystore.rs` | 独立的小改进：挡本机其它用户（挡不住同 uid） |

**覆盖范围**：目前接的是**增强侧**（`cabi.rs` 的三处 FFI 调用）。
**目标侧尚未接入**（`target_abi.rs` 的 6 处 `spawn_blocking`，即备份/恢复的真实 I/O）
—— 它需要按**每个目标实例**的配置动态生成白名单（根目录由 `url`/`fields` 指定），
比增强侧复杂。这是下一步。

**仍未解决的**：同进程**内存**仍可读（age 私钥、主口令都在宿主内存里）
⇒ 需要档位 C。本次只解决「插件读磁盘上的密钥与口令」。

## 5. 推荐路线

**分两步，而非一步到位：**

### 第一步：档位 B —— **已实施**（v0.5.2 / ADR-023）

**理由**：投入产出比最高。

1. **零契约变更** —— ABI/SDK/插件全部不动，纯宿主侧改动。
2. **挡住最现实的攻击**：恶意/被攻陷的插件读密钥库、配置、快照库。
3. **可增量验证**：先用 `example-localfs`（只写本地目录）验证白名单边界。
4. 为第二步**铺路**：如果将来上子进程，Landlock 规则集可直接复用。

**必做的验证**（本次评估已识别）：
- **插件专属线程池的上限**：每插件 1 个（或 k）线程 × N 插件；
  插件多时线程数增长，需设上限并在超限时**回退到受限的公共池**
  （注意：回退意味着那些调用**没有**沙箱保护，须记日志）。
- **插件子进程/子线程的继承行为**：已实测「施加后新建的线程与 `fork` 子进程都继承」
  ⇒ 插件自己派生的 worker 同样受限（符合预期）；但插件**不能在施加前**抢先创建线程，
  因此施加时机必须是「该插件线程首次被创建时、且在跑任何插件代码之前」。
- **实际插件能否受限运行**：`kzwr` 需要网络（已实测可只放开 443）
  与自身数据目录；`example-localfs` 只需目录读写。**应各跑一次真实备份验证**。

### 第二步（有真实需求再做）：档位 C

**触发条件**（任一）：
- 出现**第三方**插件（当前只有官方插件，信任度较高）
- 需要「插件的卡死**可强杀**」——当前看门狗只能判失败 + 泄漏线程（`PLUGIN_PLAN.md` 决策 6 的固有局限），
  这是**用户可感知**的痛点，也是子进程方案最硬的收益
- 合规/审计要求真隔离

**不建议**在没有上述触发条件时投入档位 C：
收益（挡内存读）需要叠加 Landlock 才成立，而 Landlock 第一步已经给了。

## 6. 结论

| 档位 | 隔离内存 | 隔离文件 | 隔离网络 | 契约变更 | 改动量 | 结论 |
|---|---|---|---|---|---|---|
| A 池线程+Landlock | ✗ | ✓ | ✓ | 无 | 小 | ❌ **线程污染，否决** |
| **B 专属线程+Landlock** | ✗（但挡 `/proc/<宿主pid>/mem`） | ✓ | ✓ | **无** | 中 | ✅ **已实施（v0.5.2）** |
| C 子进程+现有 ABI | ✓ | ✓ | ✓ | 部分 | 大 | 🔶 有触发条件再做 |
| D 子进程+新 IPC | ✓ | ✓ | ✓ | 全部 | 很大 | ❌ 不建议 |
| E 容器/namespace | ✓ | ✓ | ✓ | — | 中 | ❌ **本机不可用（EPERM）** |

**三句话总结**：

1. **进程隔离单独做几乎没用** —— 同 uid 子进程照样能读「`keystore.age`（密文）+
   `.passphrase`（钥匙）」并解出私钥；真正的防护是「地址空间分离 **+** 文件白名单」的组合，
   且白名单必须**两者都挡**。
2. **Landlock 是本机唯一无特权可用的强隔离原语**（ABI v7，实测可限制文件与 TCP），
   但**不可逆 + per-thread** ⇒ 绝不能施加在共享的 `spawn_blocking` 池线程上。
3. **先做档位 B**（零契约变更、挡住最现实的攻击），把档位 C 留给
   「第三方插件」或「卡死可强杀」这两个真实触发条件。

## 附：评估方法说明

本文所有结论均来自**本机实测**，不是文档推断：

- 隔离原语能力：`unshare` / `prctl` / `landlock_*` syscall 直接调用验证
- Landlock 语义：写了 4 个最小 C 程序分别验证「per-thread」「继承/不继承」
  「不可逆」「按端口白名单」
- 性能：`fork+exec` 20 次取均值
- 攻击面：对照实际代码（`keystore.rs` / `main.rs` / `target_abi.rs` 的传输路径）
  与部署权限（`config/privilege`），并用 `/proc/<pid>/status` 核实运行特权

**已按评估结论补测的项**：`/proc/<宿主pid>/mem` 在 Landlock 下**被挡**（`EPERM`），
且 `/proc/self` 需显式允许 —— 两条都已实测纳入上表。

**仍未验证的项**（实施前补测）：
- 真实插件的受限运行（`kzwr` 需 443 + 数据目录；`example-localfs` 需目录读写）
- 插件专属线程数随插件数量的增长曲线（是否需要池上限）
- `seccomp` 是否可作为 Landlock 的补充（本机 `Seccomp: 0`，
  即宿主进程当前**未**启用 seccomp —— 可考虑叠加 `no_new_privs` + 最小 seccomp 策略）
